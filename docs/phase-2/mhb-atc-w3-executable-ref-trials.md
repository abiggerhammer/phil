# W3 executable protected-ref denials — dormant source-only implementation

Tracking: [worker boundary #1863](https://github.com/abiggerhammer/phil/issues/1863), [immutable admission #1839](https://github.com/abiggerhammer/phil/issues/1839), [G1/G2 CI #1935](https://github.com/abiggerhammer/phil/issues/1935). Builds on accepted and merged [read-only W3 plan #1944](https://github.com/abiggerhammer/phil/pull/1944). **This PR must NOT activate W3 or mint either App's token.**

## Exactly what this slice implements

A new manually triggered, main-only, owner-only workflow `.github/workflows/mhb-atc-w3-ref-commissioning.yml` and strict state machine `scripts/mhb_atc_w3_ref_trial.py`. Its only future writes are operations on three disposable single-component branches covered by the admitted-ref ruleset #27365284:

- `hamster/admitted/w3-<nonce>-canary` — publisher App 5782193 creates the canary at the trusted first parent commit, verifies its SHA, deletes it and verifies absence. **No worker test begins until the publisher has proven it can perform the exact cleanup operation.**
- `hamster/admitted/w3-<nonce>-seed` — the publisher creates an exact disposable seed at that same first-parent SHA. Worker App 5836223 attempts a valid fast-forward UPDATE to trusted main, a FORCE-UPDATE toward the second ancestor, and DELETE. Each should be denied by the active ruleset, then immediately read back unchanged.
- `hamster/admitted/w3-<nonce>-create` — absent at preflight. The worker App attempts one valid CREATE at the trusted main SHA, expecting explicit repository-rules denial; it must remain absent. 

These four negative requests run **sequentially**, never in parallel. Every attempt is preceded by checking current main, live ruleset version/conditions, a complete admitted-namespace prefix snapshot, exact seed SHA and absence of the other disposable refs. Every denial must be explicit in the **status and response body**, mention repository rules **and the exact disposable ref**. A bare HTTP 422 or a generic access error does not count. Any 2xx, ambiguous error, unexpected ref motion or live state drift stops all subsequent worker attempts.

## Credential boundaries and recovery

Workflow jobs have **separate protected environments**: `atc-publisher` for canary/seed and cleanup; `atc-worker-broker` for worker denials. The key and minted token of one App are never supplied to the other job, any worker container, candidate source, artifact or URL. Both tokens are Phil-only and request only Contents write; the token's action-returned App slug and installation ID are checked and `GET /installation/repositories` must show exactly Phil before any attempted write. The worker job **repeats the byte-identical, independently accepted W1 JWT GET /app and GET /app/installations step** before minting its token; the actual minted installation ID must match the protected JWT-authenticated receipt in that same job. This is still a narrowly authorized test, not delegation to a hamster.

The `publisher_cleanup` job uses `always()` after any attempted seed job and either worker outcome. It intentionally **does not depend on the repository runtime enable variable** after the seed attempt: turning that variable OFF must not strand a protected orphan. Recovery still requires the original exact source-authorized nonce and owner/manual/first-attempt context. It reads only the three exact disposable names and can delete a ref **only** when its current SHA is one of the known, tested trusted commits. Other refs, arbitrary hashes, different nonce, main or source branches are never cleanup targets. It verifies absence after each deletion. An unexpected PR does not occur in this slice. On a failed cleanup or an unknown ref SHA: **STOP for operator and independently approved publisher recovery**; never use a maintainer PAT to work around the ruleset.

**Independent recovery dispatch, tied to the ORIGINAL trial:** The `prepare` job in `mode=run` checks source activation, the frozen target first-parent chain, all three protected-target workflow trees, their reachability from trusted current `main`, and the live read-only ruleset/namespace. It then writes a **non-secret V2 original-run binding** (`w3-origin.json`) containing the nonce, original run ID, **original owner/main dispatch SHA separately from frozen source/parent/grandparent target SHAs**, and reviewed workflow-tree SHA. The step uploads it as `mhb-atc-w3-origin` **before the publisher canary/seed job is eligible**. A later canceled-run recovery manually dispatches `mode=cleanup`, the **same source-approved nonce**, `original_run_id=<original workflow run ID>`, and `RECOVER_W3_EXACT_REFS_ONLY`. The separate run downloads the original binding using a read-only `actions:read` token. `scripts/mhb_atc_w3_provenance.py` checks its exact schema, run ID, nonce, digest and SHA strings; authenticated GitHub GET /actions/runs/<id> must confirm the original workflow path, first attempt, owner, main, and **the original head SHA**. GitHub Git-commit GETs independently reconstruct both first-parent links and validate the original **three Git workflow-tree IDs**. No user-supplied SHA can override that authenticated source. This works even after main advances by multiple unrelated commits, because cleanup uses the **original verified lineage**, never the new run's recent ancestors. Unknown refs/SHAs fail closed. The cleanup job repeats this verification **before minting its own publisher-only token**; the worker App is never invoked for recovery. Retain the approved nonce/digest until the original three refs are confirmed absent; source-policy changes may intentionally block recovery. Do not substitute a maintainer PAT or an unauthenticated local artifact.

Cleanup cannot be made perfectly atomic using GitHub's ordinary DELETE ref API. The test relies on the ruleset's exclusive publisher bypass plus a cross-ATC concurrency group and repeated exact ref reads, and does not claim protection against arbitrary external publisher writes. A cleanup job can fail to start due to platform outage or environment gating; **do not run a trial without an independent publisher recovery procedure.**

## Current-default quarantine required for DELETE

The frozen historical ref-target workflow pin does **not** cover GitHub's
default-branch workflow selection on branch deletion. Before the publisher
canary DELETE, worker negative DELETE (including unexpected success) and
each publisher cleanup/recovery DELETE, trusted main source must validate
the complete **current default-branch** workflow tree using the strict
G1/W3 semantic inventory audit, independently of the frozen target SHA.
It must reject unsafe or unsupported push/delete triggers; a harmless
additional workflow on main is acceptable if it passes semantic quarantine.
The current-default SHA and tree are recorded in `default_quarantine_checks`
separately from the frozen `workflow_tree_sha`, and a changed default
requires fresh validation before a later deletion, even during recovery.
A final authenticated main check immediately precedes DELETE; GitHub's
ordinary APIs do not provide atomicity against a concurrent main change.
See [frozen-target and current-default validation](mhb-atc-w3-frozen-targets.md).

## Sanitized durable evidence (never actual App credentials)

`scripts/mhb_atc_w3_evidence.py` writes a finite, **0600**, atomically replaced and fsynced `$RUNNER_TEMP/w3-evidence.json` receipt in each protected job. Every ref write gets an **INTENT** record *and a flushed `W3_EVIDENCE` log line before the API call*. Then it records a bounded HTTP status, exact target, pre/post ref SHA (or absence), and the **only accepted, strictly matched canonical ruleset diagnostic**. The App numeric ID and authenticated action installation ID are included; raw API payloads, arbitrary diagnostic text, JWTs, tokens and private keys are **never** serialized. An interrupted request leaves an explicit unknown/partial attempt, not a fabricated denial. A failed worker test cannot truthfully yield `DENIALS_CONFIRMED`. For tests that complete or fail on a functioning runner, a guarded `if: always()` upload step retains the curated JSON as separate job artifacts (30-day retention), without exposing App tokens. GitHub job logs provide an additional receipt line even before the artifact can be uploaded.

GitHub cancellation or platform failure can prevent artifact upload, and no GitHub API can make an isolated DELETE atomic against a concurrent separately privileged publisher action. **Do not treat a missing artifact or unknown response as proof of denial or cleanup**: use the authenticated origin binding and independent read-only live ref census to reconcile before any further authorized action. The original binding artifact is committed *before* any trial ref write, which makes this recovery procedure available even when the later credential-bearing job fails. Verify actual token revocation in the original and cleanup job logs; synthetic evidence tests cannot prove live revocation.

## What tests establish

The `scripts/test_mhb_atc_w3_ref_trial.py` suite drives a fake in-memory GitHub API. Two additional offline suites, `test_mhb_atc_w3_provenance.py` and `test_mhb_atc_w3_evidence.py`, replay stale/cross-run origin bindings, wrong first parents, incomplete historical workflow quarantines, post-main-advance cleanup identity and partial-failure sanitized evidence. It covers publisher canary create/delete before the seed, four correctly formed serial worker negative requests, denial classification, ref readback, changed-main and ruleset version, wrong SHA cleanup, no foreign ref deletion and source/run activation staying OFF. CI's ATC radar replay **never calls the live trial**. No App token, live GitHub mutation or privileged environment appears in that CI job.
